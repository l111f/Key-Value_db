# 需求规格说明书 - Key-Value DB 项目成熟化

## 1. 项目概述

### 1.1 背景

Key-Value DB 是一个基于 B+ 树索引的嵌入式键值存储引擎，使用 Rust 实现。当前版本（v0.1.0）已具备基础的存储引擎能力，包括 B+ 树索引、缓冲池管理、WAL 预写日志、ACID 事务、崩溃恢复和交互式 REPL。

然而，经过对全部源代码的逐模块分析，项目在**数据可靠性、查询能力、配置管理、命令行体验、数据完整性、运维工具**等方面存在显著的功能缺失。同时，在**工程化质量**维度上，项目也存在明显不足：模块平铺无分层目录、缺少集成测试和基准测试体系、Cargo.toml 配置极简、无代码格式化和 lint 标准、无 CI/CD 自动化流水线。

本需求文档分为两部分：**功能性需求（FR）** 聚焦数据可靠性、查询能力、配置管理等功能增强；**工程化需求（ER）** 聚焦代码规范、工程结构、测试体系、CI/CD 等生产级品质的提升。

### 1.2 目标

将现有的 Key-Value DB 从"可用的学习项目"完善为"功能完备的成熟项目"，使其具备：
- **功能维度**：完善的数据持久化与可靠性保障机制、丰富的查询与数据操作能力、灵活的配置管理与运行时控制、友好的命令行交互体验、实用的运维与管理工具
- **工程维度**：清晰的分层工程结构、统一的代码规范与风格、完善的测试体系（单元/集成/基准）、自动化 CI/CD 流水线、跨平台支持

### 1.3 范围

**包含：**
- 对现有 11 个源码模块的功能增强需求（FR 系列）
- 新增功能模块的需求定义（FR 系列）
- 工程结构优化与目录重组（ER 系列）
- 代码规范与风格标准制定（ER 系列）
- 测试体系完善（单元/集成/基准测试）（ER 系列）
- CI/CD 自动化流水线与跨平台支持（ER 系列）

**不包含：**
- 非功能性需求（性能指标定量目标、安全策略定量目标等）
- 部署需求（Docker 镜像、发布流程等）
- 项目治理文档（LICENSE、CONTRIBUTING.md、CHANGELOG.md 等）

## 2. 现有功能盘点

以下为当前项目已实现的功能清单，作为需求分析的基线：

| 模块 | 已实现功能 |
|------|-----------|
| `kv_engine.rs` | open/close、put/get/delete、scan、begin/commit/rollback |
| `btree.rs` | B+ 树插入、精确查找、删除（含分裂/合并/再平衡）、范围扫描、序列化/反序列化 |
| `buffer_pool.rs` | LRU 缓冲池、pin/unpin、脏页管理、淘汰策略、flush_all |
| `disk_manager.rs` | 页面分配/读写、WAL 文件读写、fsync、文件元数据管理 |
| `page.rs` | 4KB 固定页面、页类型标记、CRC32 校验、键数量字段、序列化/反序列化 |
| `wal.rs` | WAL 记录序列化/反序列化、append/recover/clear、CRC32 校验、LSN 管理 |
| `transaction.rs` | 单事务管理、快照回滚、WAL 记录写入、未提交数据读取 |
| `recovery.rs` | 基于 WAL 的崩溃恢复、已提交事务 Redo、未提交事务跳过 |
| `repl.rs` | 交互式 REPL、命令分词（支持双引号）、命令别名、help/status |
| `error.rs` | 统一错误枚举（9 种错误类型）、IoError 自动转换 |
| `main.rs` | 入口点、固定数据目录创建、固定数据库路径 |

## 3. 功能需求

### 3.1 数据持久化与可靠性

#### FR-001: 非事务写入的 WAL 记录

- **需求ID**: FR-001
- **优先级**: 高
- **现状问题**: 当前 `KVEngine::put()` 和 `KVEngine::delete()` 在非事务模式下直接操作 B+ 树，**不写入 WAL 日志**。这意味着非事务写入一旦遭遇崩溃，数据将永久丢失，无法通过恢复机制找回。
- **需求描述**: 非事务模式下的 `put` 和 `delete` 操作也应生成 WAL 记录。每条非事务写入作为一个独立的事务（自动 begin + commit），确保所有写操作均可通过 WAL 恢复。
- **验收标准**:
  1. 非事务模式下执行 `put` 后，WAL 文件中存在对应的 Put 记录和 Commit 记录
  2. 非事务模式下执行 `delete` 后，WAL 文件中存在对应的 Delete 记录和 Commit 记录
  3. 强制终止进程后重新打开数据库，所有非事务写入的数据均完整恢复
- **依赖关系**: 无

#### FR-002: WAL 检查点（Checkpoint）机制

- **需求ID**: FR-002
- **优先级**: 中
- **现状问题**: WAL 文件随写操作无限增长，从不截断（仅在 `close()` 时清空）。长时间运行后 WAL 文件可能膨胀至极大，且每次重启都需要从头重放全部 WAL 记录，恢复时间随运行时长线性增长。
- **需求描述**: 实现 Checkpoint 机制，定期将缓冲池中的脏页刷写到磁盘，并截断已不需要的 WAL 日志。提供手动触发 Checkpoint 的 API 和 REPL 命令。
- **验收标准**:
  1. 调用 checkpoint 后，所有脏页已刷写到磁盘
  2. 调用 checkpoint 后，WAL 文件中被已刷写数据覆盖的记录被截断
  3. Checkpoint 后重启数据库，数据完整，且不需要重放已 checkpoint 的记录
  4. REPL 中可通过 `checkpoint` 命令手动触发
- **依赖关系**: FR-001

#### FR-003: 数据库文件完整性校验工具

- **需求ID**: FR-003
- **优先级**: 中
- **现状问题**: 当数据文件因磁盘故障或意外断电损坏时，缺少主动检测和报告损坏位置的手段。虽然页面有 CRC32 校验，但只在读取时被动触发错误，无法主动全量扫描。
- **需求描述**: 提供数据库完整性校验功能，遍历所有数据页和 WAL 记录，检查 CRC32 校验和、页面结构合法性、B+ 树结构一致性（父-子指针、键有序性、叶子链表连通性）。
- **验收标准**:
  1. 可通过 API 调用 `engine.verify()` 执行全量校验
  2. 可通过 REPL 命令 `verify` 执行校验
  3. 校验结果报告：总页数、损坏页列表、B+ 树结构异常、WAL 记录异常
  4. 对完好数据库校验返回通过
  5. 对人为篡改的数据页能准确定位到损坏的页号
- **依赖关系**: 无

#### FR-004: 页面空闲回收机制

- **需求ID**: FR-004
- **优先级**: 低
- **现状问题**: B+ 树删除操作释放的页面（页号）永远不会被复用，`DiskManager::next_page_id` 单调递增。大量删除操作后，数据文件中存在大量空闲页，造成空间浪费，且文件只增不减。
- **需求描述**: 实现空闲页链表（Free List），当 B+ 树删除节点释放页面时，将页号加入空闲链表。分配新页面时优先从空闲链表取用，空闲链表为空时才递增 `next_page_id`。
- **验收标准**:
  1. 删除大量数据后，新插入的数据复用已释放的页号
  2. 数据文件大小在"删除再插入等量数据"后不增长
  3. 空闲链表信息持久化到 `.meta` 文件，重启后可恢复
  4. 数据库功能（CRUD、事务、恢复）不受空闲页回收影响
- **依赖关系**: 无

### 3.2 查询能力增强

#### FR-005: 前缀扫描（Prefix Scan）

- **需求ID**: FR-005
- **优先级**: 高
- **现状问题**: 当前 `scan` 命令只能指定 `[start, end]` 的字节范围进行扫描。在实际使用中，用户经常需要查询某个前缀下的所有键值对（如所有 `user:` 前缀的键），需要手动构造前缀的上界，不够直观。
- **需求描述**: 新增前缀扫描功能，指定一个前缀字符串，返回所有以该前缀开头的键值对。在 REPL 中新增 `prefix` 命令。
- **验收标准**:
  1. API 层面提供 `engine.prefix_scan(prefix) -> Vec<(Vec<u8>, Vec<u8>)>` 方法
  2. `prefix_scan(b"user:")` 返回所有以 `user:` 开头的键值对
  3. 前缀无匹配时返回空列表
  4. REPL 中 `prefix user:` 命令正确展示匹配结果
  5. 前缀扫描利用 B+ 树的有序性，在前缀结束后立即停止扫描，不遍历全树
- **依赖关系**: 无

#### FR-006: 逆序扫描（Reverse Scan）

- **需求ID**: FR-006
- **优先级**: 中
- **现状问题**: 当前范围扫描只能从小到大遍历（利用叶子节点 `next_leaf` 指针），无法从大到小逆序扫描。在某些场景下（如查询最新数据、倒序排列）需要逆序能力。
- **需求描述**: 支持指定扫描方向（正序/逆序）的范围扫描。当 start > end 时自动识别为逆序扫描，或在 API 中增加扫描方向参数。
- **验收标准**:
  1. API 提供逆序扫描能力，如 `engine.scan_reverse(start, end)`
  2. 逆序扫描结果按键从大到小排列
  3. REPL 中支持 `rscan <start> <end>` 命令
  4. 正序和逆序扫描结果包含相同的数据，仅顺序相反
- **依赖关系**: 无

#### FR-007: 带分页的范围扫描

- **需求ID**: FR-007
- **优先级**: 中
- **现状问题**: 当前 `scan` 一次性返回范围内所有结果。当数据量很大时（如百万级键），一次性加载全部结果会消耗大量内存，且 REPL 中会刷屏。
- **需求描述**: 范围扫描支持 `limit` 和 `offset` 参数，实现分页查询。`limit` 限制返回的最大条数，`offset` 指定跳过的前 N 条记录。
- **验收标准**:
  1. API 提供 `engine.scan_with_limit(start, end, limit, offset)`
  2. `limit=10, offset=0` 返回前 10 条
  3. `limit=10, offset=10` 返回第 11~20 条
  4. 结果数不足 limit 时返回实际数量的结果
  5. REPL 中支持 `scan <start> <end> [limit] [offset]` 格式
- **依赖关系**: 无

#### FR-008: 键存在性检查（Exists）

- **需求ID**: FR-008
- **优先级**: 低
- **现状问题**: 判断一个键是否存在需要调用 `get` 并检查返回值是否为 `None`。`get` 操作需要读取并反序列化完整的 value，当 value 很大时存在不必要的开销。
- **需求描述**: 提供 `exists` 方法，仅检查键是否存在而不读取值，避免不必要的数据拷贝。在 REPL 中新增 `exists` 命令。
- **验收标准**:
  1. API 提供 `engine.exists(key) -> bool` 方法
  2. 键存在时返回 `true`，不存在时返回 `false`
  3. REPL 中 `exists <key>` 输出存在/不存在的提示
  4. 不读取和返回 value 数据
- **依赖关系**: 无

#### FR-009: 键计数统计（Count）

- **需求ID**: FR-009
- **优先级**: 低
- **现状问题**: 获取数据库中键的总数需要执行全范围扫描 `scan("", "\xFF\xFF...")` 并计算返回列表的长度，效率极低。
- **需求描述**: 提供获取键总数的能力。通过遍历 B+ 树的叶子节点统计键数量，或维护一个全局计数器。在 REPL 中新增 `count` 命令。
- **验收标准**:
  1. API 提供 `engine.count() -> usize` 或 `engine.count_range(start, end) -> usize` 方法
  2. 返回数据库中所有键（或指定范围内键）的准确数量
  3. 插入 N 个键后 `count()` 返回 N
  4. 删除后计数相应减少
  5. REPL 中 `count` 命令展示当前键总数
- **依赖关系**: 无

### 3.3 配置管理

#### FR-010: 命令行参数支持

- **需求ID**: FR-010
- **优先级**: 高
- **现状问题**: `main.rs` 中数据库路径硬编码为 `"data/kvstore.db"`，缓冲池大小硬编码为 `1000`，B+ 树阶数硬编码为 `64`。用户无法在不修改源码的情况下更改这些参数。
- **需求描述**: 支持通过命令行参数指定数据库路径、缓冲池大小、B+ 树阶数等运行时配置。提供合理的默认值，使无参数运行时行为与当前一致。
- **验收标准**:
  1. `cargo run -- --db-path /path/to/my.db` 使用指定路径打开数据库
  2. `cargo run -- --buffer-pool-size 500` 设置缓冲池大小为 500
  3. `cargo run -- --btree-order 32` 设置 B+ 树阶数为 32
  4. `cargo run`（无参数）使用默认值，行为与当前完全一致
  5. `cargo run -- --help` 显示所有可用参数及说明
  6. 参数解析错误时给出清晰的错误提示而非 panic
- **依赖关系**: 无

#### FR-011: 配置文件支持

- **需求ID**: FR-011
- **优先级**: 低
- **现状问题**: 所有配置项分散在源码的各个模块中，修改任何配置都需要改代码重新编译。
- **需求描述**: 支持从配置文件（如 TOML 格式）读取数据库配置。配置文件包含数据库路径、缓冲池大小、B+ 树阶数、WAL 相关参数等。命令行参数可覆盖配置文件中的值。
- **验收标准**:
  1. 支持 `--config config.toml` 参数指定配置文件路径
  2. 配置文件可设置：数据库路径、缓冲池大小、B+ 树阶数
  3. 配置文件不存在时使用默认值并给出提示
  4. 命令行参数优先级高于配置文件
  5. 配置文件格式错误时给出清晰的错误提示和行号
- **依赖关系**: FR-010

### 3.4 错误处理与用户反馈

#### FR-012: 键值大小限制校验

- **需求ID**: FR-012
- **优先级**: 高
- **现状问题**: 当前 `put` 操作不对 key 和 value 的长度做任何校验。由于 B+ 树节点存储在固定的 4KB 页面中，过长的 key 或 value 会导致序列化后超出页面容量，引发数据截断或写入损坏，且没有任何错误提示。
- **需求描述**: 在 `put` 操作前校验 key 和 value 的长度，超过单个页面可容纳的最大值时返回明确的错误。根据页面布局和 B+ 树节点格式计算并暴露最大允许的键值大小。
- **验收标准**:
  1. `put` 操作在 key 过长时返回 `KvError::KeyTooLarge` 错误，包含当前 key 大小和最大允许大小
  2. `put` 操作在 value 过长时返回 `KvError::ValueTooLarge` 错误，包含当前 value 大小和最大允许大小
  3. 单个 key-value 对加上节点头部开销不超过一个页面（4KB）时可正常写入
  4. 超限写入不产生任何数据损坏或部分写入
- **依赖关系**: 无

#### FR-013: 错误类型扩展与中文错误信息

- **需求ID**: FR-013
- **优先级**: 中
- **现状问题**: 当前 `KvError` 仅有 9 种错误变体，且错误信息全部为英文，而 REPL 的用户提示为中文，风格不一致。缺少对常见错误场景的覆盖，如无效参数、数据库文件版本不兼容、磁盘空间不足等。
- **需求描述**: 扩展 `KvError` 枚举以覆盖更多错误场景，并为 REPL 场景提供中文错误提示。错误信息应包含足够的上下文（如具体的键名、大小、限制值等）帮助用户理解和定位问题。
- **验收标准**:
  1. 新增错误类型至少覆盖：KeyTooLarge、ValueTooLarge、InvalidArgument、DatabaseVersionMismatch
  2. REPL 中所有用户可见的错误信息使用中文
  3. 错误信息包含具体的上下文数据（如 `put "very_long_key" 失败: 键大小 5000 字节超过最大限制 4080 字节`）
  4. 库级别 API 的错误描述（`Display` trait）保持英文，REPL 层做翻译
- **依赖关系**: FR-012

#### FR-014: 操作结果反馈增强

- **需求ID**: FR-014
- **优先级**: 低
- **现状问题**: REPL 中的操作反馈过于简单。`put` 只返回 "OK"，不显示是插入还是更新；`delete` 只返回 "OK - 已删除" 或 "(nil)"；`status` 仅显示是否打开和是否在事务中。
- **需求描述**: 增强各操作的反馈信息，提供更有意义的操作结果。
- **验收标准**:
  1. `put` 新键时输出 "OK - 已插入 (1 个键)"，覆盖已有键时输出 "OK - 已更新 (key: xxx)"
  2. `delete` 输出被删除键的名称
  3. `status` 显示更多信息：数据库路径、键总数、已使用页数、缓冲池使用率、当前事务 ID 等
  4. `scan` 在结果首行显示扫描范围，末尾显示总条数和耗时
- **依赖关系**: FR-009

### 3.5 REPL 与命令行体验

#### FR-015: 命令历史记录

- **需求ID**: FR-015
- **优先级**: 中
- **现状问题**: 当前 REPL 使用 `std::io::stdin().read_line()` 读取输入，不支持上下箭头翻阅历史命令，不支持行内编辑（如 Ctrl+A 跳行首、Ctrl+U 清行）。每次输入错误都需要重新手动输入完整命令。
- **需求描述**: REPL 支持命令历史记录，包括上下箭头翻阅历史、基本的行编辑快捷键。历史记录在会话间持久化保存。
- **验收标准**:
  1. 上箭头 ↑ 可浏览上一条历史命令，下箭头 ↓ 可浏览下一条
  2. 支持基本的行编辑：Ctrl+A（行首）、Ctrl+E（行尾）、Ctrl+U（清除行）、Backspace/Delete
  3. 退出 REPL 后重新打开，历史命令仍然可用
  4. 历史记录保存到文件（如 `.kvdb_history`），可配置最大条数
- **依赖关系**: 无

#### FR-016: 批处理文件执行

- **需求ID**: FR-016
- **优先级**: 中
- **现状问题**: 批量初始化数据或执行预设操作时，只能手动逐条输入命令，无法从文件中批量加载执行。
- **需求描述**: 支持从文件读取并批量执行 REPL 命令。可通过命令行参数指定批处理文件路径。
- **验收标准**:
  1. `cargo run -- --file init.kvdb` 从文件读取命令并逐条执行
  2. 批处理文件每行一条 REPL 命令，语法与交互式 REPL 完全一致
  3. 支持注释行（以 `#` 开头的行被忽略）
  4. 支持空行（被忽略）
  5. 批处理中遇到错误时的处理策略：默认继续执行并输出错误信息，支持 `--stop-on-error` 参数在首条错误时停止
  6. 批处理完成后输出执行摘要：成功 N 条，失败 M 条
- **依赖关系**: FR-010

#### FR-017: 数据导出与导入

- **需求ID**: FR-017
- **优先级**: 中
- **现状问题**: 无法将数据库中的数据导出为可读格式，也无法从外部文件批量导入数据。数据迁移和备份只能依赖底层的文件拷贝，不够直观和可控。
- **需求描述**: 提供数据导出和导入功能。导出将数据库中的键值对序列化为文本格式；导入从文本文件读取键值对并写入数据库。
- **验收标准**:
  1. REPL 命令 `export <file_path>` 将数据库中所有键值对导出到指定文件
  2. 导出格式为每行一条记录：`key<TAB>value`，key 和 value 使用 hex 或 escaped 编码
  3. REPL 命令 `import <file_path>` 从指定文件读取键值对并写入数据库
  4. 导入文件格式与导出格式一致
  5. 导出后清空数据库再导入，数据完整一致
  6. 导出文件中包含头部注释说明格式和导出时间
- **依赖关系**: 无

#### FR-018: 优雅退出与数据保护

- **需求ID**: FR-018
- **优先级**: 中
- **现状问题**: 当 REPL 中存在未提交事务时输入 `exit`，程序直接关闭数据库，未提交的事务修改会被静默提交到 B+ 树（因为 `close` 只做 flush_all 和清空 WAL，不回滚事务）。用户可能意外丢失未提交的事务数据。
- **需求描述**: 退出 REPL 时检查是否存在未提交事务，若有则提示用户选择提交、回滚或取消退出。
- **验收标准**:
  1. 有未提交事务时输入 `exit`，显示 "存在未提交事务，请选择：[C]提交 / [R]回滚 / [Esc]取消"
  2. 选择提交后正常关闭
  3. 选择回滚后回滚事务再关闭
  4. 选择取消后回到 REPL 继续操作
  5. 无未提交事务时 `exit` 行为与当前一致
- **依赖关系**: 无

### 3.6 事务功能增强

#### FR-019: 事务自动回滚（超时机制）

- **需求ID**: FR-019
- **优先级**: 低
- **现状问题**: 用户开启事务后忘记提交或回滚（如离开终端），事务会一直持有，后续所有写操作都在此事务上下文中执行。长时间未提交的事务会导致 WAL 无限增长，且事务内修改对其他操作不可控。
- **需求描述**: 为事务增加可选的超时机制，超过指定时间未提交的事务自动回滚。
- **验收标准**:
  1. 开启事务时可指定超时时间：`begin --timeout 30`（30 秒）
  2. 无参数 `begin` 不设置超时（保持当前行为）
  3. 事务超时后自动回滚，REPL 中显示 "事务已超时并自动回滚 (txn_id: N)"
  4. 超时后再执行事务内操作返回 `NoActiveTransaction` 错误
  5. 可通过配置文件设置全局默认事务超时时间
- **依赖关系**: FR-011

#### FR-020: 事务内写操作即时 WAL 记录增强

- **需求ID**: FR-020
- **优先级**: 低
- **现状问题**: 事务内的写操作已经记录到 WAL，但 `commit` 时 flush_all 的策略是全量刷写，即所有脏页（包括非事务产生的脏页）都会被写入磁盘。这在语义上没有问题，但在效率上有优化空间。
- **需求描述**: 事务提交时仅刷写该事务修改涉及的脏页，而非全量刷写。追踪每个事务修改的页面集合。
- **验收标准**:
  1. 事务提交时仅刷写该事务涉及的脏页
  2. 不影响其他未提交事务的脏页
  3. 功能正确性不变：提交后数据持久、回滚后数据恢复
- **依赖关系**: 无

### 3.7 运维与管理功能

#### FR-021: 数据库空间紧凑化（Compaction）

- **需求ID**: FR-021
- **优先级**: 低
- **现状问题**: 大量删除操作后，数据文件中存在空闲页和碎片空间，但文件大小不会缩小。长时间使用后可能造成磁盘空间浪费。
- **需求描述**: 提供数据库紧凑化功能，重建 B+ 树到新的数据文件，去除空闲页和碎片空间，减小文件体积。
- **验收标准**:
  1. API 提供 `engine.compact() -> Result<CompactionStats>` 方法
  2. 紧凑化后数据文件大小不大于紧凑化前
  3. 紧凑化后所有键值对数据完整可访问
  4. 紧凑化过程中如果出错，原数据文件不被破坏
  5. REPL 中 `compact` 命令触发紧凑化并输出前后文件大小对比
  6. 返回统计信息：原文件大小、新文件大小、回收空间、处理页数
- **依赖关系**: FR-004

#### FR-022: 运行时统计信息

- **需求ID**: FR-022
- **优先级**: 中
- **现状问题**: `status` 命令仅显示数据库是否打开和是否在事务中，缺少运行时的详细统计信息，无法评估数据库的使用状况和系统健康度。
- **需求描述**: 扩展 `status` 命令，展示详细的运行时统计信息。
- **验收标准**:
  1. `status` 命令展示以下信息：
     - 数据库路径和打开状态
     - 键总数（total_keys）
     - 已使用页数（used_pages）和总页数（total_pages）
     - 缓冲池使用率（frames_used / capacity）
     - 缓冲池命中率（hits / (hits + misses)）
     - 当前活跃事务 ID（若有）
     - WAL 文件大小
     - 数据文件大小
  2. 新增 `stats` 命令展示操作计数：put_count、get_count、delete_count、scan_count
  3. 提供重置统计计数器的命令 `stats reset`
- **依赖关系**: FR-009

#### FR-023: 数据库重建/修复工具

- **需求ID**: FR-023
- **优先级**: 低
- **现状问题**: 当数据文件严重损坏（如 `.meta` 文件丢失、根节点页号未知、部分页面损坏）时，当前没有修复手段，只能接受数据丢失。
- **需求描述**: 提供数据库修复功能，尝试从 WAL 日志重建丢失或损坏的数据。支持忽略损坏页面、从 WAL 全量重建 B+ 树等策略。
- **验收标准**:
  1. `.meta` 文件丢失时，可通过扫描所有页面重建根节点信息
  2. 部分页面损坏时，可通过 WAL 日志恢复可恢复的数据
  3. 提供 `--repair` 命令行参数进入修复模式
  4. 修复过程输出详细的修复日志：跳过的损坏页、恢复的记录数、丢失的数据量
  5. 修复完成后数据库可正常打开和使用
- **依赖关系**: FR-001, FR-003

### 3.8 数据操作便捷性

#### FR-024: 批量操作接口（Batch Put/Delete）

- **需求ID**: FR-024
- **优先级**: 低
- **现状问题**: 批量插入或删除数据时，需要循环调用 `put` / `delete`，每次调用都独立经过完整的事务/WAL/缓冲池路径，无法批量优化。
- **需求描述**: 提供批量操作接口，接受一组键值对进行批量写入或一组键进行批量删除，在单个事务内完成。
- **验收标准**:
  1. API 提供 `engine.batch_put(vec![(key1, val1), (key2, val2), ...])` 方法
  2. API 提供 `engine.batch_delete(vec![key1, key2, ...])` 方法
  3. 批量操作在单个事务内完成，要么全部成功，要么全部回滚
  4. 批量操作中某一条失败时，整个批次回滚
  5. REPL 中支持从文件批量加载：`load <file_path>`（与 FR-017 的 import 功能互补，load 不需要导出格式）
- **依赖关系**: 无

#### FR-025: 键重命名（Rename）

- **需求ID**: FR-025
- **优先级**: 低
- **现状问题**: 重命名一个键需要先 get 旧值、put 新键、delete 旧键三个步骤，且中间状态对事务外的读操作可见。
- **需求描述**: 提供原子的键重命名操作，在单个操作内完成 get+put+delete。
- **验收标准**:
  1. API 提供 `engine.rename(old_key, new_key) -> Result<()>` 方法
  2. 旧键不存在时返回 `KeyNotFound` 错误
  3. 新键已存在时覆盖其值
  4. 重命名操作在事务内时与其他事务操作具有相同的原子性保证
  5. REPL 中 `rename <old_key> <new_key>` 命令可用
- **依赖关系**: 无

## 6. 假设和约束

### 6.1 假设

- 项目仍为单机嵌入式存储引擎，不涉及分布式或网络通信
- **核心存储引擎（B+ 树、缓冲池、磁盘管理、WAL、事务、恢复）保持零外部依赖**，仅使用 Rust 标准库实现
- **工程化外围层（CLI、错误处理、测试、文档构建）允许引入必需的标准 crate**（如 `clap` 命令行解析、`thiserror` 错误派生、`serde` 序列化、`criterion` 基准测试等），但不得在核心引擎模块中引入任何外部依赖
- 数据库单进程访问，不涉及多进程并发（因此无需文件锁等机制）

### 6.2 约束

- 页面大小固定为 4KB，B+ 树节点的键值容量受此限制
- 单事务模型（一次只允许一个活跃事务），嵌套事务为明确不支持的设计决策
- 所有需求不得引入破坏现有 API 兼容性的变更（可增加新 API，不可删除或改变已有 API 的签名）
- 工程化需求不得改变核心存储引擎（btree/buffer_pool/disk_manager/wal/transaction/recovery/page）的零依赖原则
- 外部依赖仅限于工程化外围层（CLI、错误处理、测试框架、文档工具），且需通过审核确认必要性

  3. 执行 `cargo clippy -- -D warnings` 无任何警告（零警告门槛）
  4. CI 流水线中包含 clippy 检查步骤（与 ER-011 关联）

  2. 所有 `pub` 结构体、枚举、函数、方法均有 `///` 文档注释
  3. 添加 `#![warn(missing_docs)]` 确保 API 文档完整性
  4. `cargo doc --no-deps` 成功生成文档，无 missing_docs 警告
  5. 文档注释中包含至少一个代码示例，展示核心 API 用法
  6. CI 流水线中包含文档构建步骤（与 ER-011 关联）
- **依赖关系**: ER-011

#### ER-007: 错误处理规范化

- **需求ID**: ER-007
- **优先级**: 中
- **现状问题**: 当前 `KvError` 手动实现了 `Display` trait，但 `KvError` 缺少 `std::error::Error` trait 的实现（即 `source()` 方法），导致无法通过 `?` 操作符被上层标准库错误自动捕获。错误类型的手动实现繁琐且易遗漏。
- **需求描述**: 引入 `thiserror` crate 简化错误类型定义，实现 `std::error::Error` trait，确保错误链可追溯。
- **验收标准**:
  1. `Cargo.toml` 中在 `[dependencies]` 添加 `thiserror`（允许引入的外围层 crate）
  2. `KvError` 使用 `#[derive(thiserror::Error)]` 替代手动 `Display` 实现
  3. `KvError` 自动实现 `std::error::Error` trait，包含 `source()` 方法
  4. 包装错误（如 `IoError`）通过 `#[error(transparent)]` 或 `#[from]` 正确传播
  5. 现有所有测试通过，错误处理行为不变
  6. 核心引擎模块（btree/buffer_pool 等）不直接依赖 thiserror，仅 error.rs 使用
- **依赖关系**: 无

### 7.3 测试体系

#### ER-008: 集成测试体系搭建

- **需求ID**: ER-008
- **优先级**: 高
- **现状问题**: 当前所有 69 个测试均为模块内单元测试（`#[cfg(test)] mod tests`），没有独立的 `tests/` 集成测试目录。集成测试从外部消费者视角验证库的公共 API，是生产级项目不可或缺的测试层级。
- **需求描述**: 在 `tests/` 目录下建立集成测试体系，从库的公共 API 视角覆盖端到端场景。
- **验收标准**:
  1. `tests/` 目录包含以下集成测试文件（每个聚焦一个场景维度）：
     - `basic_crud.rs` — 端到端 Put/Get/Delete/Scan 全流程
     - `transaction.rs` — 事务 Begin/Commit/Rollback 及持久化恢复
     - `persistence.rs` — 数据写入→关闭→重开的持久化验证
  2. 每个集成测试文件使用独立临时数据库文件（通过 tempfile）
  3. `cargo test --test <name>` 独立执行每个集成测试文件
  4. `cargo test`（无参数）同时执行单元测试和集成测试
  5. 集成测试不依赖内部实现细节，仅通过 `kv_engine::KVEngine` 公共 API 操作
- **依赖关系**: ER-002

#### ER-009: 测试工具模块

- **需求ID**: ER-009
- **优先级**: 中
- **现状问题**: 各模块的单元测试中存在大量重复的测试初始化代码（如创建临时数据库、插入测试数据集），缺少共享的测试工具模块来减少重复并统一测试辅助方法。
- **需求描述**: 创建测试工具模块，提供可复用的测试辅助函数、测试夹具和测试数据生成器。
- **验收标准**:
  1. 新增 `src/test_utils.rs`（仅在 `#[cfg(test)]` 下编译）
  2. 提供以下辅助工具：
     - `create_temp_db() -> KVEngine` — 创建使用临时文件的数据库实例
     - `generate_sequential_keys(n: usize) -> Vec<Vec<u8>>` — 生成有序测试键
     - `generate_random_kv(count: usize) -> Vec<(Vec<u8>, Vec<u8>)>` — 生成随机键值对
     - `assert_engine_contains(engine, key, expected_value)` — 断言辅助方法
  3. 单元测试和集成测试均可引用这些工具方法
  4. 消除至少 3 个模块中重复的数据库初始化代码
- **依赖关系**: ER-008

#### ER-010: 基准测试框架

- **需求ID**: ER-010
- **优先级**: 中
- **现状问题**: 项目完全没有性能基准测试，无法量化评估 CRUD、范围扫描、事务提交等核心操作的性能特征，也无法在代码变更后检测性能回归。
- **需求描述**: 引入 `criterion` 基准测试框架，为核心操作建立性能基线测试。
- **验收标准**:
  1. `Cargo.toml` 在 `[dev-dependencies]` 添加 `criterion`
  2. 新增 `[[bench]]` 配置段，声明基准测试 target
  3. `benches/` 目录包含 `crud_bench.rs`，覆盖以下基准场景：
     - `bench_put` — 批量插入性能（不同数据规模）
     - `bench_get` — 点查性能（命中 vs 未命中）
     - `bench_scan` — 范围扫描性能（不同范围大小）
     - `bench_delete` — 删除性能
  4. `cargo bench` 成功执行并输出性能统计报告
  5. 基准测试使用独立临时数据库，互不干扰
  6. 每个基准测试包含合理的数据预热阶段
- **依赖关系**: ER-001、ER-002
